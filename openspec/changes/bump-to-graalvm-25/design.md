## Context

The `project-scaffolding` change stood up the native image on **GraalVM community
21 / JDK 21** with **native-build-tools 0.10.4** and Gradle 8.11.1. Because that
toolchain predates the unified reachability-metadata format (introduced in GraalVM
for JDK 23, fully migrated at JDK 25), the tracing agent produced five split
`*-config.json` files, and `app/build.gradle.kts` wires them in with explicit
`-H:*ConfigurationResources` build args. Two metadata sets coexist under
`META-INF/native-image/com.rewear/`: `app/` (agent-generated) and `extra/` (a
hand-maintained Flyway-plugin safety net the agent run did not exercise).

GraalVM 25 is the current LTS (JDK 25, Sept 2025); native-build-tools has moved to
the 1.1.x line. This is a deliberate, low-risk maintenance bump — the current setup
works and the deprecated per-file format is still accepted — so correctness is
gated on the existing native smoke test, not on new behavior. See `proposal.md` for
motivation. Relevant decision records: ADR-10 (linux/amd64 only), ADR-12 (photo
resize path), ADR-13 (native image + R2DBC, with blocking-JDBC fallback).

## Goals / Non-Goals

**Goals:**
- Move the whole toolchain to JDK 25 / GraalVM 25 LTS consistently (buildSrc
  toolchain, both Dockerfiles, CI `setup-java`).
- Adopt the unified single-file `reachability-metadata.json` format and delete the
  five split config files.
- Remove the now-redundant explicit `-H:*ConfigurationResources` build args, relying
  on classpath auto-detection from `META-INF/native-image/**`.
- Preserve the Flyway-plugin metadata safety net (migrated to the unified format, or
  confirmed unnecessary under GraalVM 25).
- Prove equivalence: native build + smoke test (`/health`, migrations, resize path)
  pass on the new toolchain.

**Non-Goals:**
- No product, domain, or runtime API behavior changes.
- No move off R2DBC to the blocking-JDBC fallback (ADR-13) — that stays a
  documented escape hatch, not part of this change.
- No k3s / deployment-topology changes; prod stays Docker Compose.
- Not bumping unrelated library versions (Kotlin, Ktor, Exposed, Flyway) beyond what
  JDK 25 / native-build-tools 1.1.x compatibility forces.

## Decisions

**1. Bump JDK 21 → 25 in one atomic change across every touch point.**
The JDK version appears in four places — `buildSrc` `jvmToolchain(21)` +
`JvmTarget.JVM_21`, `Dockerfile.jvm` (`eclipse-temurin:21-{jdk,jre}`),
`Dockerfile.native` (`native-image-community:21`), and CI `setup-java`. These must
move together or the JVM tests, fat jar, and native binary would build against
different JDKs. *Alternative considered:* bump native only, keep JVM on 21 — rejected
because the JVM path is what runs the tests that gate the native build, so a version
skew would mean the smoke test validates a different bytecode target than dev/test.

**2. Adopt the unified `reachability-metadata.json`, regenerated by the JDK 25 tracing
agent driven by the test suite.** The single-file format is the supported path on GraalVM
25 and is auto-detected from `META-INF/native-image/**`, which lets us drop the explicit
resource args. Rather than manually running the app, we run the agent via native-build-tools
`./gradlew -Pagent test` — the tests exercise the smoke-test paths, making regeneration
reproducible. *Alternative considered:* hand-merge the five files — rejected; the agent output
is the source of truth. **Two hard-won caveats (see Decision 8):** (a) the agent only records
what the tests actually execute, so every response type must have a test that serializes it —
we added `ResizeCheckRouteTest` because no test hit `/internal/resize-check`, and its
`ResizeCheckResponse` serializer was silently missing; (b) the JVM agent **cannot** capture
AWT/Java2D **JNI** metadata at all.

**3. Drop the explicit `-H:*ConfigurationResources` build args; keep `--no-fallback`,
headless AWT, and `ReportExceptionStackTraces`.** Once metadata is a single
auto-detected file, the four resource args are redundant. *Alternative considered:*
keep them pointing at the unified file for explicitness — rejected as it re-introduces
the brittle path coupling this change exists to remove.

**4. Re-evaluate `--initialize-at-build-time` on GraalVM 25 rather than assume it
carries over.** The current list (logback/slf4j + a handful of Kotlin enums/intrinsics)
was tuned for GraalVM 21. Newer native-image may already handle some of these, or may
need different entries. We treat the existing list as the starting point and trim/adjust
only if the build demands it, documenting any change.

**5. Drop the Flyway `extra/` net; keep a hand-maintained net for AWT JNI instead.** The
original `extra/` net existed because the first agent run didn't exercise Flyway. Our
test-driven agent run *does* (the Testcontainers migration test), and a static check confirmed
every real class in the old `extra/reflect-config.json` is now covered — so the Flyway net is
removed. But the resize smoke test exposed a *different* gap the net was never about: AWT/Java2D
**JNI**. See Decision 8.

**8. Split metadata into two auto-detected unified files by provenance.** Native-image merges
every `reachability-metadata.json` under `META-INF/native-image/**`, so we keep two:
- `com.rewear/app/reachability-metadata.json` — **agent-owned** (reflection + resources).
  Fully regenerable via `-Pagent test`; overwrite it wholesale on each regen.
- `com.rewear/awt/reachability-metadata.json` — **hand-maintained** `jni` block (54 AWT/Java2D
  entries: `sun.java2d.loops.*`, `java.awt.image.*`, JPEG codec callbacks, …). The native
  `libawt` calls back into Java via JNI; the JVM agent can't observe this (on the JVM, AWT/JNI
  works without any GraalVM config), so it is carried over from the old `jni-config.json`,
  converted to the unified schema (`name`→`type`, `[L…;`→`…[]`), and never touched by regen.
This separation is why the earlier single-file approach was wrong: a regen would silently wipe
the JNI block and crash the resize path at `Toolkit.loadLibraries`. *Alternative considered:*
one merged file — rejected; regeneration is destructive and the JNI block isn't agent-derivable.
One resource (`System$LoggerFinder`) is also re-added post-regen, as the agent doesn't trace it.

**6. Accept the forced toolchain cascade that JDK 25 triggers.** Implementation proved the
"bump Gradle only if the plugin requires it" assumption wrong — it is the *JDK*, not the
plugin, that forces the bumps, and they are mandatory and larger than anticipated:
- **Gradle 8.11.1 → 9.7.1** — 8.11.1's bundled Kotlin DSL compiler throws
  `IllegalArgumentException: 25` parsing the JDK version, so it cannot run on JDK 25.
  Unavoidable: both Dockerfiles and CI run Gradle *inside* JDK-25-only environments, so a
  "run Gradle on JDK 21 via toolchain" workaround does not apply. Major-version bump with its
  own breaking-change surface, gated by the existing build + tests.
- **Kotlin 2.1.0 → 2.2.21** — 2.1.0 cannot run on JDK 25; 2.2.20+ adds JDK 25 support.
- **Ktor 3.0.3 → 3.5.2** — second-order: Gradle 9 removed the `mainClassName` property that
  Ktor 3.0.3's bundled Shadow plugin still maps; 3.5.x uses the maintained `com.gradleup.shadow`.

**7. Target JVM 24 bytecode, not 25.** No released Kotlin exposes `JvmTarget.JVM_25` (the enum
maxes at `JVM_24` through 2.2.21), so JVM 25 bytecode is not yet emittable. The toolchain runs
on GraalVM 25 (`jvmToolchain(25)`) while compiling to JVM 24; Java source/target compatibility
is pinned to 24 to satisfy Kotlin's JVM-target validation. Costs nothing functionally — GraalVM
25 native-image and the JDK 25 runtime both consume JVM 24 bytecode — and can be lifted to 25
once Kotlin supports it. *Alternative considered:* keep the previous JVM 21 target — equally
valid, but 24 tracks the toolchain more closely.

## Risks / Trade-offs

- **New metadata gaps or init-time behavior changes under GraalVM 25** → The native
  smoke test (`/health`, Flyway migrations, ADR-12/13 resize path) is the gate; a
  regression shows up there before merge, not in prod.
- **Gradle 9 major bump brings its own breaking changes** → Larger surface than a patch
  bump (config cache, removed APIs like `mainClassName`); gated by the existing build +
  full test suite, which pass on GraalVM CE 25. The Ktor 3.5.2 bump already absorbed the
  one breakage this surfaced.
- **Removing the Flyway `extra/` safety net silently breaks migrations in native** →
  Mitigated by Decision 5: keep it unless a build without it passes the migration smoke
  test.
- **Ktor 3.0.3 → 3.5.2 API drift** → A five-minor-version jump could change server APIs;
  bounded by the green compile + full test suite. Larger than a maintenance bump implies,
  but forced by Gradle 9 (Decision 6).
- **Overall rollback is cheap** → Every change is a version pin or a metadata file;
  reverting the commit restores the working GraalVM 21 setup. The deprecated per-file
  format still being accepted bounds the blast radius.

## Migration Plan

1. Bump the toolchain cascade (Decision 6): native-build-tools 1.1.12, Gradle 9.7.1,
   Kotlin 2.2.21, Ktor 3.5.2; target JVM 24 (Decision 7).
2. Bump JDK 21 → 25 across buildSrc, both Dockerfiles, and CI; confirm JVM build + tests
   pass on 25.
3. Regenerate reachability metadata with the JDK 25 tracing agent against the dev stack;
   replace the five split files with the unified file; migrate the Flyway `extra/` net.
4. Simplify the `graalvmNative` block (drop resource args; re-evaluate init-at-build-time).
5. Run the native build + smoke test; confirm `/health`, migrations, and resize path pass.
6. Update README (tech-stack/notes) and add a `docs/ROADMAP.md` follow-up entry.

**Rollback:** revert the change commit — restores GraalVM 21 pins and the split-file
metadata, both still valid.

  Gradle 9.7.1. See Decision 6.
- ~~Does JDK 25 force any in-scope library bumps (Kotlin/Ktor/Exposed)?~~ **Resolved:** yes —

  Exposed 1.0.0-beta-2 unaffected. Bytecode target capped at JVM 24 (Decision 7). Verified by a
  green `./gradlew build` + full test suite on GraalVM CE 25.
- ~~Can the Flyway `extra/` safety net be dropped?~~ **Resolved:** yes — the test-driven agent
  run covers Flyway (static check + green migration smoke test). But a new hand-maintained net
  was required for AWT/Java2D JNI, which the agent cannot derive (Decisions 5 & 8).
